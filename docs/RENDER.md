# Deploying to Render

The archive is designed to run on Render from this repository with no manual
steps beyond setting one variable. This document explains what gets deployed,
what the platform's limits cost you, and what to do when something does not work.

## What you get

Three resources, declared in [`render.yaml`](../render.yaml):

| Resource | What it is | Why it exists |
| --- | --- | --- |
| `archive-db` | Managed PostgreSQL 16 | The archive is built on `tsvector`, `pgvector` and `pg_trgm`, which SQLite cannot render at all. |
| `archive` | Web service, one port | Serves the built interface *and* the API from a single origin. |
| `archive-worker` | Background worker | Drains the job queue: backfills, OCR, graph extraction, refreshes. |

There is no Redis. The queue backend is the database, which is slower and
entirely adequate at this volume, and it is one fewer service to pay for.

## Deploying

1. Push this repository to GitHub.
2. In Render: **New → Blueprint**, and point it at the repository.
3. Render reads `render.yaml` and creates all three resources.
4. Set `PUBLIC_BASE_URL` to the address the service was given. Render marks it
   `sync: false`, so it will prompt you. It appears in citation links and on the
   offline page, so it has to be the address a reader actually visits.

The signing secret and the database password are generated by Render. Neither is
in the repository, and the archive refuses to start without a real
`JWT_SECRET` — see [The production guard](#the-production-guard).

The first boot runs the Alembic migrations and then imports the corpus. The
import is skipped once the archive is populated, so a restart costs one query
rather than a full reindex.

## One port, not two

Render gives a service one listening port, so there is nowhere to put nginx in
front. FastAPI serves the built interface instead, which is what
[`Dockerfile.render`](../Dockerfile.render) and
[`app/core/spa.py`](../apps/api/app/core/spa.py) are for.

The trade, stated plainly: static files now pass through Python, so a large asset
is slower to serve than it would be behind nginx. For an archive of text that
costs nothing worth optimising, and in exchange there is one origin, no CORS to
configure, and no second process to supervise. The kiosk arrangement in
[`Dockerfile`](../Dockerfile) still uses nginx, where there is a machine to put
it on.

Two details that are easy to get wrong, and are pinned by tests:

- **The catch-all is registered last.** Starlette matches routes in the order
  they were added, so an interface route added before the API's would answer
  `/api/v1/health` with a page of HTML and every endpoint would return 404 with
  no other symptom. `mount_interface` warns about this, and
  `tests/test_spa.py` and `tests/test_openapi_schema.py` both fail if it is
  reversed.
- **Environment variable names have no prefix.** `Settings` has no `env_prefix`;
  only the hardware profile uses `HW_`. So `DHA_DATABASE_URL` is not a variant
  of `DATABASE_URL` — it is a variable the process never reads. Every deployment
  file in this repository once used that prefix, and a container built from them
  came up in development mode with the shipped signing secret and looked healthy.
  `tests/test_deployment_config.py` now checks every deployment file against the
  real settings on every CI run.

## The production guard

`app/core/production_guard.py` refuses to start when `ENVIRONMENT=production` and
any of these are true:

| Refused | Why |
| --- | --- |
| `JWT_SECRET` is the shipped default, blank, or under 32 characters | Anyone who has read this repository could mint an archivist session. |
| `DEBUG=true` | Error responses include internals. |
| `DEMO_MODE=true` | This archive is about not inventing records. Serving invented ones, even labelled, is not a mode to deploy. |
| `DATABASE_URL` points at SQLite | It cannot hold the full-text and vector types; the service would start and then fail on the first search. |
| `CORS_ORIGINS` contains `*` | Credentials are enabled, and browsers reject that combination. |

It never fires in development, where a refusal would be a nuisance rather than a
protection.

An empty `CORS_ORIGINS` is explicitly *not* a problem. Both supported
arrangements serve the interface and the API from one origin, so a browser never
makes a cross-origin request and no CORS headers are needed at all.

## What the free tier costs you

Worth reading before you rely on this for anything:

- **The web service sleeps** after a period of inactivity, and the first request
  after that takes tens of seconds. Fine for a demonstration; bad for anything
  with a user waiting.
- **The database is destroyed after 30 days.** This is the important one. A
  demonstration loses its uploads, its OCR work and any accounts created through
  the interface. The corpus is re-imported on the next boot, so the site comes
  back, but anything a visitor contributed does not.
- **Uploads and OCR output are ephemeral.** `STORAGE_BACKEND=filesystem` writes
  to the container's own disk, which is discarded on every deploy. Attach a disk
  or point `STORAGE_BACKEND` at an object store if that matters.
- **Background workers are a paid feature.** Deleting the `archive-worker` block
  from `render.yaml` leaves the site working: the corpus is embedded and
  searchable, and only the deferred work stops running. Nothing a first-time
  visitor does depends on it.

## The honest limitations of a public deployment

These are properties of the archive, not of the platform, and they are worth
stating in a submission:

- **Every record is `unverified_secondary`.** The stored text is a summary of a
  cited source, not a transcription of it. Promoting a record to
  `verified_primary` requires a person to check it against the original, and that
  has not been done for any record. See [`HONESTY.md`](HONESTY.md).
- **Search is lexical, not semantic.** With no embedding provider configured the
  archive falls back to deterministic hashed embeddings, which support keyword
  search and exact-phrase matching but not "find me the speech about X" in the
  general sense. The health endpoint says which mode is active.
- **Answers are extractive.** With no language model configured, the archive
  quotes the passages it found and states its uncertainty. It does not write
  prose about Ambedkar's views, which is the right default for this material.

## When something does not work

**The build fails on `pgvector`.** The initial migration creates the `vector`
and `pg_trgm` extensions itself (`CREATE EXTENSION IF NOT EXISTS` in
`ad2a75161e01_initial_archive_schema.py`), so a first deploy needs no manual
step. If the deploy role is not permitted to create extensions, the migration
fails with `permission denied to create extension`; create them once as the
database owner, then redeploy:

    psql "$DATABASE_URL" -c 'CREATE EXTENSION IF NOT EXISTS vector'
    psql "$DATABASE_URL" -c 'CREATE EXTENSION IF NOT EXISTS pg_trgm'

**The worker log says it is waiting for the schema.** On a cold start the worker
and the web service start together, and only the web service runs migrations. The
worker waits up to two minutes for the schema rather than exiting, so a normal
start is a short pause. If it reports that the wait expired, the web service
migrated later than two minutes, or failed — read the web service log.

**The service will not start, and the log says so.** That is the production guard
doing its job. The message names the variable. Set it.

**The interface loads but every request 404s.** Almost always the interface
routes being registered before the API's. The log will show HTML where JSON was
expected.

**`PUBLIC_BASE_URL` is wrong.** Citation links and the offline page point
somewhere useless. Set it and redeploy.

## Deploying somewhere else

The same image works anywhere that runs a container and assigns `$PORT`. On a
machine you control, [`docker-compose.yml`](../docker-compose.yml) is the better
arrangement: it puts nginx in front, keeps uploads on a named volume, and does
not stop while you are looking at it.
